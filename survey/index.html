    调研目标与核心问题¶

    本次调研旨在系统理解 Harness 的概念、技术体系、现有实现及其对 Agent 能力的影响，并进一步探索 Harness 的优化方法及其与 Recursive Self-Improvement（RSI）的关系。

    围绕这一目标，调研主要回答以下六个核心问题：

    第一部分：概念与发展脉络¶

    Harness 是什么？它与 Agent、Workflow、Scaffold、Framework 等相关概念有何区别？

    明确 Harness 的定义、概念边界与发展历程，理解其在 Agent 系统中的定位。

    第二部分：技术体系与设计空间¶

    Harness 由哪些核心机制组成？有哪些可以独立研究和优化的技术维度？

    建立 Harness 的技术分类体系，分析不同模块的作用、设计选择及潜在优化空间。

    第三部分：现有工具与实现分析¶

    主流 Agent 工具如何实现 Harness？它们在架构与设计决策上有哪些异同？

    以典型 Coding Agent 为主要对象，结合架构与源码分析，理解不同 Harness 的实现方式及其设计权衡。

    第四部分：实证研究与效果评价¶

    如何定量评价 Harness 的有效性？哪些设计真正能够提升 Agent 的能力？

    重点研究 2026 年的 Harness-Bench 和 HarnessOpt-Bench，分析其评测目标、实验设计、指标体系、主要发现及局限性。

    第五部分：实践与优化探索¶

    如何构建、使用、改造以及自动优化 Harness？

    分别从使用者、开发者和研究者三个视角展开实践，探索 Harness 的配置、实现、实验评估与自动优化方法。

    第六部分：未来发展与 RSI¶

    Harness 能否成为实现 Recursive Self-Improvement（RSI）的一条可行路径？

    研究自动化 Harness Engineering、自我改进机制与递归优化的关系，分析现有进展、技术瓶颈及潜在研究方向。

    Agent Harness 概念辨析¶

    Agent 系统可以拆解为一个相对清晰的结构：

    $$ \text{Agent System} = \underbrace{\text{Foundation Model}}{\text{能力核心}} + \underbrace{\text{Harness}} $$}} + \underbrace{\text{Environment/Tools}}_{\text{能够作用于什么}

    如果进一步讨论系统的演化，则需要引入改进循环：

    $$ \text{Improvement Loop}: A_t \rightarrow \text{Experience/Eval} \rightarrow \text{Modify} \rightarrow A_{t+1} $$

    后者才真正进入 self-improvement 和 recursive self-improvement (RSI) 的范畴。

    Microsoft 在其官方文档中将 agent harness 定义为把语言模型转化为可执行 agent 的 "runtime scaffolding"：负责驱动模型调用、工具调用、上下文/状态管理、审批策略，并让 agent 在多步任务中持续执行[1]。OpenAI 也明确使用 "Codex harness" 这个术语，并将 managed harness 与 SDK/runtime、sandbox 等概念区分开来[2]。

    1. Harness 的定义¶

    以一个典型的 Coding Agent 为例：

                       +---------------+
                   |      LLM      |
                   |  GPT / Claude |
                   +-------+-------+
                           |
                    next action?
                           |
              +------------v------------+
              |        Harness          |
              |                         |
              | context construction    |
              | agent loop              |
              | tool dispatch           |
              | memory / state          |
              | retry / recovery        |
              | permission / approval   |
              | verification            |
              | compaction              |
              | sub-agent orchestration |
              +------+----------+-------+
                     |          |
             +-------v--+  +----v-------+
             |  Tools   |  |  Sandbox   |
             | shell    |  | repo / OS  |
             | search   |  | browser    |
             | editor   |  | VM         |
             +----------+  +------------+

    Harness 既不是单纯的 prompt，也不是 agent loop 的同义词。

    它实际控制的是整个执行流程：

    $$ H: (O_t, S_t, G) \rightarrow C_t \rightarrow M \rightarrow A_t \rightarrow E \rightarrow O_{t+1} $$

    其中： - $G$：目标 - $S_t$：agent 当前状态 - $O_t$：之前的观察 - $C_t$：真正喂给模型的上下文 - $M$：foundation model - $A_t$：模型输出的动作 - $E$：环境

    这个视角解释了为什么单纯说 "GPT-X 在 SWE-Bench 上得分多少" 已经不够准确。更完整的表述应该是：

    $$ \text{Performance} = f(M, H, E, B) $$

    即 model + harness + environment + benchmark 的函数。

    已有研究工作（如 HarnessBench[3]）开始采用固定模型、改变 harness 的实验范式来专门研究这一层的影响。

    2. Harness vs Agent¶

    这是需要首先明确的区分。

    概念 Agent Harness
    定义 完整的行为主体 支撑 Agent 运行的外层机制
    是否包含模型 通常包含 通常不包含 foundation model 本身
    功能 完成任务 让模型能够持续完成任务
    示例 coding agent context + loop + tools + verification + permissions
    关注点 agent 能完成什么 如何让 agent 完成得更可靠

    可以近似理解为：

    $$ \text{Agent} \approx \text{Model} + \text{Harness} $$

    但这不是严格定义，因为不同文献对于 environment、memory、data store 是否属于 agent 的划分并不统一。

    更完整的系统建模是：

    $$ \text{AgentSystem} = (M, H, E, S) $$

    其中 $M$ 是模型，$H$ 是 harness，$E$ 是环境，$S$ 是状态。

    3. Harness vs Framework¶

    这是目前最容易混淆的两个概念。

    例如： - LangGraph - AutoGen - CrewAI - Agents SDK

    这些更偏向 framework / SDK。

    Framework 提供的是构建组件：

    node
edge
agent
tool
handoff
state
graph
callback

    开发者用这些组件构建出一个 Harness。

    可以理解为：

    $$ \text{Framework} \xrightarrow{\text{programming}} \text{Harness} $$

    Framework 回答的是：

    "用什么工具写 agent system？"

    Harness 回答的是：

    "这个 agent 实际运行时，周围的系统是什么？"

    OpenAI 当前文档的划分很典型：Agents SDK 让开发者控制 agent loop、tools 和 orchestration，而 Agents API 可以直接运行 OpenAI 管理的 Codex harness[2]。

    类比：

    PyTorch       → framework
trained model → artifact/system

LangGraph     → framework
具体的 agent  → harness + model

    4. Harness vs Runtime¶

    两者重合较多，且目前社区没有完全统一的术语标准。

    可以采用如下边界划分：

    Runtime¶

    关注的是：

    process
container
compute
scheduling
persistence
checkpoint
resource isolation
RPC

    即：agent 在哪里运行。

    例如：

    Docker
VM
cloud sandbox
process manager
GPU/CPU allocation

    Harness¶

    关注的是：

    what context?
which tool?
when retry?
how verify?
when stop?
which subagent?
when ask user?
what gets remembered?

    即：agent 怎么运行。

    可以理解为：

    $$ \text{Runtime} \approx \text{execution substrate} $$

    $$ \text{Harness} \approx \text{agent execution semantics} $$

    实际产品实现中 Harness 经常包含 Runtime，因此边界会模糊。DigitalOcean、Microsoft 等的文档也存在略有不同的划分方式[1,4]。这应该被视为工程分类学（taxonomy），而非已经标准化的计算机科学术语。

    5. Harness vs Workflow¶

    这个区别在系统设计中很重要。

    Anthropic 的定义是[5]：

    Workflow：LLM 和工具按预定义路径运行。

    而 Agent：

    模型动态决定自己的执行过程和工具调用。

    因此：

    Workflow
A → B → C → D

    控制流主要来自程序逻辑。

    而 agent loop：

                +-----------+
            |    LLM    |
            +-----+-----+
                  | decide
                  v
                tool?
              /   |   \
          read  edit  shell
              \   |   /
                  v
             observation
                  |
                  +-----> LLM

    控制流主要由模型产生。

    关键点在于：

    Harness 可以承载 workflow，也可以承载 autonomous agent。

    例如：

    Harness
 +-- predefined outer workflow
 |
 +-- planner agent
 +-- coding agent
 +-- reviewer agent
 |
 +-- verifier

    Workflow 是 control-flow pattern；

    Harness 是 承载这些 control flow 的系统层。

    6. Harness vs Orchestrator¶

    Orchestrator 范围更窄。

    它回答的是：

    "谁应该执行下一步？"

    例如：

    Manager
 +-- Researcher
 +-- Coder
 +-- Reviewer

    需要处理：

    routing
handoff
parallelism
task decomposition
subagent spawning

    这些属于 Harness 的一部分：

    $$ \text{Orchestration} \subset \text{Harness} $$

    但 Harness 还包含：

    context management
memory
tool protocol
sandbox
verification
permissions
retry strategy
state persistence

    因此不能将 harness 简化为 multi-agent orchestration。

    7. Harness vs Agent Loop¶

    这个更容易区分。

    最简单的 agent loop：

    while not done:
    response = model(context)

    if response.tool_call:
        observation = execute(response.tool_call)
        context.append(observation)
    else:
        done = True

    这只是 Harness 的核心控制循环。

    一个真正复杂的 harness 包含：

    Prepare context
     ↓
Model
     ↓
Parse action
     ↓
Policy check
     ↓
Execute sandbox
     ↓
Observe
     ↓
Validate
   ↙   ↘
pass   failure
 ↓       ↓
state   recovery
 ↓       ↓
compact/retrieve
     ↓
 next iteration

    $$ \text{AgentLoop} \subset \text{Harness} $$

    8. Harness vs Context Engineering¶

    这对后续研究问题的识别尤其重要。

    Context engineering 回答的是：

    这一轮 Model 到底看到什么？

    例如：

    system prompt
conversation history
repository map
relevant files
memory
tool outputs
summaries
skills
retrieved documents

    可以表示为：

    $$ C_t = \text{Select}(G, \text{History}, \text{Memory}, \text{Files}, \text{Observations}) $$

    典型研究问题包括：

    context selection
context compression
retrieval
memory management
summarization
context ordering
context budgeting

    Context Engineering 是 Harness 的子集：

    $$ \text{ContextEngineering} \subset \text{HarnessEngineering} $$

    完整的 Harness 包含：

    Harness
+-- Context
+-- Memory
+-- Tools
+-- Loop
+-- Planning
+-- Verification
+-- Recovery
+-- Permission
+-- Orchestration

    这个划分在 practitioner 社区越来越常见[6]，但同样不是严格标准；有些研究将 tool selection 也纳入 context engineering 的范畴。

    9. Harness vs Prompt Engineering¶

    Prompt engineering 的范围更窄：

    Prompt Engineering
↓
"告诉模型什么"

    例如：

    Before editing the code, inspect all call sites.

    而 harness engineering 可能直接写成：

    files = search_call_sites(symbol)

if not files:
    reject_edit()

context.add(files)

    二者的根本区别是：

    Prompt¶

    希望模型遵守规则：

    $$ P(\text{model obeys rule}) $$

    Harness¶

    程序直接强制执行：

    $$ \text{rule} = \text{deterministic} $$

    例如：

    prompt:
"请运行测试。"

vs

harness:
edit 后如果没有 test execution，
不允许 terminate。

    后者体现了 Harness 研究的一个重要思想：

    不依赖模型"记得做"，而是改变系统结构，使它"必须做"。

    10. Harness vs Tool / MCP¶

    MCP (Model Context Protocol) 是另一个层次的抽象。

    MCP 本质上解决的是：

    $$ \text{Agent 如何标准化地访问外部能力} $$

    例如：

    read_file()
search()
browser()
database()
github()
slack()

    Tool/MCP 负责：

    interface definition
schema
discovery
invocation
result transport

    Harness 决定：

    什么时候调用？
把哪个 tool 暴露给模型？
是否需要 approval？
结果如何进入 context？
失败后是否 retry？
连续调用多少次？
tool output 是否可信？

    $$ \text{MCP/Tools} \subseteq \text{Harness capability surface} $$

    MCP 并不等同于 Harness。

    11. Harness vs Environment / Sandbox¶

    Environment 是：

    agent 行动发生的世界。

    对于 coding agent：

    repository
filesystem
terminal
OS
compiler
tests
browser

    Harness 是：

    agent 与这个世界交互的机制。

    类比强化学习：

    $$ \text{Agent} \xrightarrow{\text{action}} \text{Environment} $$

    $$ \text{Environment} \xrightarrow{\text{observation}} \text{Agent} $$

    在 LLM agent 中，Harness 很大程度上实现了这个 interface。

    例如：

    Model:
"运行 rm -rf /"

Harness:
permission check
        ↓
blocked

Environment:
根本没收到 action

    Sandbox 是 Harness 可以控制/调用的基础设施，但不是 Harness 本身。

    12. Harness vs Scaffold¶

    这个词在研究论文中经常出现，且与 Harness 非常接近。

    Agent scaffold 通常指：

    foundation model 外面的 prompting、tooling、control logic。

    过去常见的表述：

    LLM + scaffold

    现在越来越多的表述：

    LLM + harness

    二者大体等价：

    $$ \text{Scaffold} \approx \text{Harness} $$

    但在语义侧重上仍有区别：

    Scaffold Harness
    更偏研究原型 更偏完整运行系统
    prompting / loop / tool use context + tools + state + sandbox + verification + permissions...
    often benchmark-oriented often production-oriented
    边界相对松散 越来越指完整 execution layer

    在较早的 agent 论文中看到：

    "We optimize the agent scaffold."

    不应急于认为这是另一个方向。

    很可能用当前术语会表述为：

    harness optimization。

    13. Harness vs Agent Architecture¶

    Architecture 是更上位的概念。

    例如：

    Planner
   ↓
Executor
   ↓
Critic
   ↓
Memory

    这是 architecture。

    Harness 是这个 architecture 的可执行实现：

    谁什么时候运行
context 怎么传递
工具如何执行
state 怎么保存
错误如何处理
termination 怎么判断

    可以近似理解为：

    $$ \text{Architecture} = \text{design} $$

    $$ \text{Harness} = \text{operationalization}(\text{design}) $$

    14. Harness 与 Self-Improving Agent 的关系¶

    到这里开始与 self-improvement 和 RSI 的讨论真正连接起来。

    普通 Harness：

    $$ H_{t+1} = H_t $$

    每次任务流程：

    task
 ↓
agent
 ↓
trajectory
 ↓
answer

    结束。

    Self-improving agent：

    task
 ↓
Harness H_t
 ↓
trajectory
 ↓
evaluation
 ↓
discover failure
 ↓
modify harness
 ↓
Harness H_{t+1}

    即：

    $$ H_{t+1} = U(H_t, \tau_t, R_t) $$

    其中： - $\tau_t$：execution trajectory - $R_t$：evaluation signal - $U$：improvement algorithm

    可能修改的对象包括：

    prompt
context policy
memory
tools
skills
planning strategy
workflow
verification logic
retry strategy
agent code itself

    这引出了一个重要概念：

    $$ \text{Harness Self-Improvement} $$

    这是 Harness → RSI 的桥梁。

    2026 年最新的 self-improving agents survey 恰好采用了这个拆分：将 agent 建模为

    $$ x_t = (M_t, H_t, D_t, T_t, \text{Imp}_t) $$

    其中： - $M$：foundation model - $H$：harness - $D$：data system - $T$：trainer - $\text{Imp}$：improvement mechanism[7]

    15. Self-improvement 与 RSI 的区别¶

    这里存在另一个容易混淆的点。

    假设 agent 自动修改自己的 prompt：

    $$ H_0 \rightarrow H_1 $$

    这可以称为 self-improvement。

    但严格来说，这未必是强意义上的 recursive self-improvement。

    真正的 recursion 是：

    $$ H_0 \xrightarrow{\text{Imp}_0} H_1 \xrightarrow{\text{Imp}_1} H_2 \xrightarrow{\text{Imp}_2} \cdots $$

    并且进一步：

    $$ \text{Imp}_{t+1} \neq \text{Imp}_t $$

    即：

    系统不仅能改善自己的能力，还能改善"改善自己的方法"。

    这是 RSI 最核心的 recursive 特性。

    16. Harness 与 RSI 的层次关系¶

    可以绘制为：

    Level 0
Foundation Model
       ↓
       M

Level 1
Agent Harness
       ↓
    M + H
       ↓
capable agent

Level 2
Harness Optimization
       ↓
search / optimize H
       ↓
better agent

Level 3
Self-Improving Harness
       ↓
agent analyzes trajectories
       ↓
modifies H itself

Level 4
Recursive Self-Improvement
       ↓
agent modifies H
       ↓
and modifies how H is improved
       ↓
and potentially M/D/T/Imp themselves

    这个层次结构说明：

    Harness 不是 RSI 的竞争概念，而很可能是通向 practical RSI 的核心研究对象。

    最近已经出现针对 agent harness 自我改进的研究工作，探索 agent 如何自动迭代 prompt、control flow、tools、memory 和 context management，同时处理这种优化导致的 benchmark overfitting 问题；这类研究报告了 in-distribution improvement，并重点考察了 OOD generalization[8]。

    另一个相关工作让 research agent 修改自己的代码，再通过 benchmark 筛选修改后的版本，形成连续的 self-improvement chain[9]。

    这两个例子说明：

    Harness research
          ↓
Harness optimization
          ↓
Automated harness optimization
          ↓
Self-improving harness
          ↓
Recursive self-improvement

    正在形成一条连续的研究路线。

    17. 概念分类体系¶

    观察 agent 论文时，可以用以下 taxonomy 判断研究重点：

    层次 概念 核心问题
    Intelligence Foundation Model 模型本身具备什么能力
    Instruction Prompt Engineering 如何告诉模型做什么
    Information Context Engineering 每一步给模型看什么
    Action Tool / MCP 模型能够调用什么
    Control Agent Loop / Workflow 下一步如何决定
    Coordination Orchestration 多 agent / 多任务如何组织
    Execution Runtime / Sandbox 在哪里、如何安全运行
    System Harness 上述组件如何组合成可靠 agent
    Learning Agent Learning 如何利用经验改进
    Meta-learning Harness Optimization 如何找到更好的 harness
    Evolution Self-Improving Agent agent 如何修改自己的系统
    Recursive Evolution RSI 如何持续改善自己，甚至改善 improvement mechanism

    18. 判断方法¶

    观察一个新的 "Agent 技术" 时，可以问三个问题：

    第一问：改变的是 $M$ 还是 $H$？¶

    例如：

    fine-tuning        → M
RL                 → M
new context policy → H
memory             → H
tool design        → H
planner            → H
verification       → H
subagents          → H

    第二问：改变发生在 run 内还是 run 间？¶

    run 内：
reflection
retry
replanning

    通常仍是普通 agent execution。

    而：

    run 1 → learn → modify system → run 2

    才开始进入 persistent self-improvement。

    第三问：谁在修改？¶

    human modifies H
        ↓
Harness engineering

optimizer searches H
        ↓
Harness optimization

agent modifies H
        ↓
Self-improving agent

agent modifies H + modification mechanism
        ↓
RSI

    核心总结¶

    $$ \text{Model 决定能力上限，Harness 决定如何把能力变成行动，RSI 决定这个系统如何自己改变。} $$

    Framework、runtime、workflow、orchestration、context engineering、MCP 等概念，基本都可以放在这三个核心问题周围：

                     +-------------+
                 |    Model    |
                 | intelligence|
                 +------+------+
                        |
           +------------v------------+
           |         Harness         |
           |                         |
           | prompt / context        |
           | loop / workflow         |
           | tools / MCP             |
           | memory                  |
           | orchestration           |
           | verification / recovery |
           | permission / sandbox    |
           +------------+------------+
                        |
                        v
                    Environment

              ^
              | modify
      +-------+----------+
      | Self-Improvement |
      |      / RSI       |
      +------------------+
