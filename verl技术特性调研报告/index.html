    verl 关键技术特性调研报告（实操侧）¶

    调研日期：2026-08-10 参考版本：verl 0.7（含 v0.8 / v0.9 路线图） 关注点：对新技术的支持程度 + 具体怎么用 配套报告：《RL算法调研报告.md》（算法侧）

    0. 摘要与选型判断¶

    verl 是什么： ByteDance Seed 开源的 LLM RL 后训练框架，HybridFlow 论文（EuroSys 2025）的官方实现。仓库已从 volcengine/verl 迁到 verl-project/verl，老链接是重定向。

    为什么它是当前的事实标准： DAPO、Dr.GRPO、Entropy-Mechanism、MiniMax-M1、Qwen3 系列的公开 RL 工作基本都跑在 verl 或其 fork 上。50+ 社区项目基于它。这意味着论文里的算法你大概率能直接找到配置脚本，而不用自己复现。

    0.7 版本的架构定性： 分成 verl-core（4 个可插拔组件：model engine / rollout engine / checkpoint engine / transfer queue）+ verl-trainer（3 条流水线：on-policy / one-step-off-policy / fully-async）。这个分层意味着换后端不需要改调用方代码。

    本报告最需要注意的三条：

    1. MTP 目前只支持 Megatron-Bridge + megatron 组合，且依赖大量未合并的 PR（见 §7）。RL 场景下 MTP 是"能跑但还不成熟"，官方明确把「MTP RL 训练」列在 v0.8 路线图里。
    2. 0.7 有破坏性变更：SPMD rollout 模式被移除，server mode 成为唯一选项。 升级要改代码。
    3. 训练-推理不一致的校正（rollout correction）是 verl 最有实操价值的特性，官方称其配置预设经过"数万 GPU 小时"验证，开销仅 ~1% 显存 / 1-3% 算力。建议无论跑什么算法都先打开监控。

    1. 能力矩阵总览¶

    1.1 后端支持¶

    类别 支持项
    训练引擎 FSDP、FSDP2、Megatron-LM、Megatron-Bridge、VeOmni（alpha）、TorchTitan
    推理/rollout 引擎 vLLM（0.12.0）、SGLang（0.5.6）、HF Transformers、TensorRT-LLM（初步）
    硬件 NVIDIA GPU、AMD ROCm（MI300X/MI325X/MI355X）、Ascend NPU
    实验跟踪 wandb、swanlab、mlflow、tensorboard、Prometheus/Grafana

    训练后端选型（官方给的对比表）：

    后端 并行方式 性能 模型覆盖 新模型跟进延迟
    FSDP FSDP + SP Dense 中等 / MoE 低 全部 transformer 模型 Day 0
    MCore (Megatron) DP+TP+PP+EP+CP 高 按 Megatron-Bridge 列表 数周到一个月
    VeOmni FSDP+SP+EP 中等 按 VeOmni 列表 约 1 周

    选型建议： 中小模型（≤30B）或需要尝鲜新模型 → FSDP；大 MoE（Qwen3-235B、DeepSeek-671B）追求吞吐 → Megatron。MTP 只有 Megatron 路线可用。

    1.2 内置算法¶

    verl 内置（无需自己实现）：

    PPO、GRPO、GSPO、CISPO、SAPO、DAPO、Dr.GRPO、ReMax、REINFORCE++、RLOO、PRIME、PF-PPO、KL-Cov、Clip-Cov、OPO、GPG、OTB（Optimal Token Baseline）、DPPO（Divergence PPO）、OPD（On-Policy Distillation）、DRO（Direct Reward Optimization）、SPIN、SPPO

    其中 CISPO 和 SAPO 是 0.7 新增——也就是说算法侧报告里提到的最新两个 IS 软化方法已经可以直接用。

    1.3 关键工程特性清单¶

    • Flash Attention 2、sequence packing、DeepSpeed Ulysses 序列并行
    • LoRA（含 RL 场景）、Liger-kernel
    • MoE 专家并行、router replay（vLLM 实验性）
    • FP8 rollout / FP8 端到端、NVFP4 QAT
    • 多轮对话 + 工具调用（Agent Loop）
    • 模型型奖励 + 函数型奖励 + 混合奖励
    • 容错 checkpoint、full determinism（可复现训练）
    • 三条异步流水线（on-policy / one-step-off / fully-async）
    • rollout KV cache offload（Mooncake-Store）
    • 性能分析：verl profiler、Nsight Systems、PyTorch profiler

    2. 架构：HybridFlow 与 verl-core¶

    2.1 Hybrid-Controller 编程模型¶

    verl 的核心设计是 single-controller + SPMD workers：

    • 单控制器 RLTrainer 负责编排（MPMD 风格），只发指令和元数据
    • SPMD workers 干重活（分布式前反向）
    • Ray placement group 支撑 ResourcePool / WorkerGroup 抽象，让 actor / critic / reward / rollout 四个角色既能共享 GPU 又保持隔离

    这个设计的实际好处：写一个新算法时，你写的是单进程视角的编排代码，不用手写集合通信。

    2.2 verl-core 的四个可插拔组件（0.7 新架构）¶

    组件 作用 接口
    Model Engine 训练侧引擎抽象 initialize、optimizer_zero_grad、optimizer_step、lr_scheduler_step、forward_backward_batch、get_per_tensor_param、to
    Rollout Engine 推理侧引擎抽象 chat_completion、generate（实现 AsyncServerBase 即可接新引擎）
    Checkpoint Engine 跨节点权重同步 send_weights / receive_weights，后端 NCCL（broadcast）/ NIXL（P2P）
    Transfer Queue 数据流与控制流分离 零拷贝 tensor 传输、RDMA

    加一个新训练后端不需要改调用方任何代码——这是 0.7 重构的主要收益。

    2.3 TransferQueue（实验性，v0.8 将成默认）¶

    要解决的问题： 原来 RLTrainer 同时承载控制流和数据流，成了分发瓶颈。多模态负载和 router replay 把这个问题放大了。（他们试过用 Ray object store，因为缺少 tensor 优化和列级访问而效果不佳。）

    现在的做法： trainer 只发指令和元数据，数据按引用传递。针对 PyTorch tensor 做了零拷贝和 RDMA 优化，可扩展到 ZeroMQ、NIXL、Ray RDT。

    0.7 里已支持多数据分区 + 更快的 tensor 零拷贝序列化。

    2.4 v0.8 / v0.9 路线图（对我们做技术选型很重要）¶

    v0.8 计划： - DataProto 废弃，改用 TensorDict + nested tensors（去掉 padding 开销） - 新 model engine 成为默认，fsdp_workers.py / megatron_workers.py 标记废弃 - MTP RL 训练（重点，见 §7） - 长上下文的细粒度激活重计算 / offload - DeepSeek V3.2 支持 - TensorRT-LLM rollout - vLLM worker 从 trainer 进程分离，走 CUDA IPC 更新权重 - TransferQueue 合入主线

    v0.9 计划： - fully-async 合入主线 - 移除 legacy model engine - omni-model RL 训练（Qwen3-Omni、BAGEL）、vllm-omni rollout - SWEAgent / GUIAgent recipe

    判断： 如果我们现在开始接入，建议直接按 0.7 的新 model engine + TensorDict 方向写，避免 v0.8 的废弃冲击。

    3. 算法配置速查：怎么把论文变成配置¶

    这一节是最直接可用的部分——把算法侧报告里的方法映射到实际配置。

    3.1 GRPO 基线¶

    algorithm.adv_estimator: grpo
actor_rollout_ref.rollout.n: 16                    # group size，DAPO 用 16，GRPO 常用 64
data.train_batch_size: 512
actor_rollout_ref.actor.ppo_mini_batch_size: 64
actor_rollout_ref.actor.ppo_epochs: 1
actor_rollout_ref.actor.clip_ratio: 0.2
actor_rollout_ref.actor.loss_agg_mode: token-mean
actor_rollout_ref.actor.use_kl_loss: true
actor_rollout_ref.actor.kl_loss_coef: 0.001
actor_rollout_ref.actor.kl_loss_type: low_var_kl

    loss_agg_mode 四个选项，直接对应不同论文：

    值 对应
    token-mean Dr.GRPO / DAPO 推荐（默认）
    seq-mean-token-mean 复现原始 GRPO
    seq-mean-token-sum —
    seq-mean-token-sum-norm Dr.GRPO 专用

    3.2 Dr.GRPO¶

    algorithm.norm_adv_by_std_in_grpo: false           # 关键：去掉 /std
actor_rollout_ref.actor.loss_agg_mode: seq-mean-token-sum-norm
actor_rollout_ref.actor.loss_scale_factor: <常数>   # 可选归一化常数

    3.3 DAPO 四件套¶

    # 1. Clip-Higher
actor_rollout_ref.actor.clip_ratio_low: 0.2
actor_rollout_ref.actor.clip_ratio_high: 0.28

# 2. Dynamic Sampling（超采样 3x 再过滤）
data.gen_batch_size: 1536
data.train_batch_size: 512
algorithm.filter_groups.enable: true
algorithm.filter_groups.metric: acc
algorithm.filter_groups.max_num_gen_batches: 10     # 设为非正数 = 不限重试

# 3. Token-level Loss
actor_rollout_ref.actor.loss_agg_mode: token-mean

# 4. Overlong Reward Shaping
data.max_response_length: 20480
reward_model.overlong_buffer.enable: true
reward_model.overlong_buffer.len: 4096              # 缓冲区，惩罚在此区间线性渐增
reward_model.overlong_buffer.penalty_factor: 1.0

# reward manager 要换
reward_model.reward_manager: dapo                   # GRPO 用 naive
# DAPO 不用 KL
algorithm.use_kl_in_reward: false
actor_rollout_ref.actor.use_kl_loss: false

    官方复现脚本（recipe/dapo/，都锁定 commit 4f80e4）：

    脚本 AIME 2024 资源
    run_dapo_qwen2.5_32b.sh 52% 16×8×H800
    run_dapo_wo_ds_qwen2.5_32b.sh 50% 16×8×H800
    run_dapo_early_qwen2.5_32b.sh 44% 16×8×H20

    注意：recipe/dapo 分支是冻结的"原样复现"版本，main 上的同名目录跟随新特性演进。

    一个已知坑： 开 CUDA graph（enforce_eager=False）可能导致模型性能下降，原因官方尚未定位。

    3.4 熵干预（Clip-Cov / KL-Cov）¶

    bash recipe/dapo/7b_kl_cov.sh      # 单机 Qwen2.5-7B
bash recipe/dapo/32b_kl_cov.sh     # 多机 Qwen2.5-32B

    数据用 DAPO-Math-17k。具体的协方差阈值和系数需要读脚本，文档页面没列配置键。

    3.5 长度与截断的健康指标¶

    一条实用经验：clip_ratio 超过 0.1 通常意味着过度截断，此时应该提高 max_response_length 或清理数据。

    4. Rollout Correction：verl 最有价值的特性¶

    如果这份报告只有一节值得读，是这一节。 它解决的是 RL 训练崩溃的头号元凶。

    4.1 verl 对问题的定性¶

    verl 列出了五种 off-policy 来源： 1. rollout 与训练的精度/后端差异（FP8/BF16、vLLM/SGLang vs FSDP/Megatron） 2. 异步设置里的 stale checkpoint 3. replay buffer 4. 本身就 off-policy 的算法（behavioral cloning、DAPO） 5. 数据过滤或重加权

    它明确指出常见 bug：很多实现把 π_old 当作行为策略，完全忽略 π_rollout。 并强调 "This is not PPO's fault - PPO itself is mathematically correct."——错的是假设，而这个错误假设导致训练崩溃。

    4.2 两个正交机制¶

    机制 作用方式 输出
    IS weights 连续重加权 rollout_is_weights
    Rejection Sampling (RS) 二元过滤 modified_response_mask（被拒 token 置 0）

    两者可独立或同时启用。

    IS 权重的固定流水线： 

    安全边界  exp(clamp(log_ratio, -20, 20))     # 约 2e-9 ~ 5e8
截断      .clamp(max=rollout_is_threshold)   # 这就是 TIS 的 T
padding   置零
可选      batch 归一化

    关键设计：只截上界不截下界——"保留了小权重情形下的无偏性"。

    4.3 方法清单¶

    方法 说明 推荐阈值
    Token-TIS 逐 token ratio，独立截断 1.5 – 5.0
    Seq-TIS ρ_seq = ∏ρ_t，乘性，对离群更敏感 2.0 – 10.0
    Seq-MIS Seq-TIS + 序列级拒绝 —
    Geo-RS seq_mean_k1 —
    K3-RS seq_mean_k3，小 KL 下更稳 —
    IcePop 阈值写成 "0.5_5.0"，band 外权重归零，不动 response_mask —

    Seq-TIS vs Seq-MIS 的选择： 数据干净、mismatch 中等 → Seq-TIS（"最大化信息效率"）；mismatch 严重、高权重样本大概率是垃圾 → Seq-MIS（"作为硬信任域过滤器"）。

    RS 选项是规范化字符串，逗号分隔。聚合方式 token / seq_sum / seq_mean / seq_max；估计器 k1（-log r）/ k2（0.5·(log r)²）/ k3（exp(log r) - 1 - log r）。k1 取 "lower_upper" 双边界，k2/k3 只取正上界。seq_max 只能配 k2/k3。

    4.4 两种运行模式¶

    Decoupled 模式（bypass_mode: false）：三个策略都在，通过 actor.compute_log_prob() 算 π_old。好处是 batch size 不变性 + 两种 drift 分别校正，代价是多一次前向。

    Bypass 模式（bypass_mode: true）：令 π_old = π_rollout，省掉那次前向。loss_type 二选一： - ppo_clip（默认）—— ratio π_θ/π_rollout 隐式完成 IS - reinforce —— 显式即时 IS 权重，无裁剪

    官方推荐 bypass 模式作为基线。

    4.5 配置¶

    algorithm:
  rollout_correction:
    rollout_is: token              # token | sequence | null
    rollout_is_threshold: 2.0      # float，或 "0.5_5.0" 走 IcePop
    rollout_is_batch_normalize: false
    rollout_rs: null               # 如 "seq_mean_k1"、"token_k1,seq_max_k2"

    预设（强烈建议用预设而非手调） —— RolloutCorrectionConfig 提供：decoupled_token_is()、decoupled_seq_is()、decoupled_seq_is_rs()、decoupled_geo_rs()、decoupled_k3_rs()、bypass_ppo_clip()、bypass_pg_is()、disabled() 等。文档称这些组合经过"数万 GPU 小时"验证。Token IS + token RS、纯 token RS、纯 sequence RS 也能跑但需手配。

    4.6 官方推荐的三步上线路径¶

    第一步：只观测

  → 看 rollout_corr/kl、log_ppl_abs_diff、chi2_token，摸清 gap 大小

第二步：离群多就先加 RS
  → 只过滤，不动梯度

第三步：指标合理后再加 IS 校正

    4.7 健康阈值（照着这个建 dashboard）¶

    指标 健康范围
    rollout_is_mean 接近 1.0（< 0.5 或 > 2.0 报警）
    rollout_is_eff_sample_size > 0.3（1/mean(w²)，占 batch 比例）
    rollout_is_std < 1.0
    \|kl\| < 0.1
    chi2_token < 1.0

    排障： IS 分布过宽 → 收紧阈值或换更激进的聚合；均值偏离 1.0 → 先确认 calculate_log_probs=True 且 rollout logprob 真的传到了 helper，再查系统性偏移。

    开销：约 1% 显存、1-3% 算力。 这个价格买训练稳定性非常划算。

    5. 三条流水线：同步 / 半异步 / 全异步¶

    5.1 选型¶

    流水线 特点 适用
    on-policy rollout 与训练串行，GPU 共置，算法严格正确 建立 baseline
    one-step-off-policy 用上一步参数生成下一批，与当前训练重叠；资源隔离 通用提效，效率提升 20%–40%
    fully-async trainer 与 rollouter 分离节点，流式传输 + staleness 控制 + partial rollout 128+ GPU 或长 CoT

    5.2 为什么需要异步：长尾问题¶

    关键洞察（官方原话的要点）： 在 colocate 模式下，给 rollout 更多资源也解决不了慢样本造成的空转。资源隔离后，rollout 和 train 各自的时间可能都变长了（各自资源变少），但两者的重叠降低了端到端时间。

    这是理解异步收益的正确心智模型——不是"让某一步更快"，而是"让空转时间被填满"。

    5.3 fully-async 架构¶

    四个组件： 1. Rollouter —— 逐样本生成，受新鲜度限制约束 2. MessageQueue —— 暂存生成的样本 3. Trainer —— 从队列取样本，训练若干步后触发参数同步 4. ParameterSynchronizer —— 基于 NCCL 的参数同步

    资源隔离是硬性要求：与 hybrid_engine 不同，Rollouter 和 Trainer 使用独立计算资源，必须分别指定。

    5.4 配置¶

    # 资源分配（必须分开指定）
trainer.nnodes: 4
trainer.n_gpus_per_node: 8
rollout.nnodes: 4
rollout.n_gpus_per_node: 8

# 核心异步参数
async_training.trigger_parameter_sync_step: <N>   # 多少次本地更新后同步参数
async_training.staleness_threshold: 0.5           # 允许的陈旧样本比例
async_training.require_batches: <N>               # 一次取几个 ppo_mini_batch_size
async_training.partial_rollout: true              # 同步时是否中断并恢复进行中的 rollout

# 数据（注意这里换了语义）
rollout.total_rollout_steps: <总样本数>            # 取代 train_batch_size * steps
data.gen_batch_size: 1                            # 流式

    staleness_threshold 的语义： - = 0 → 同步训练。两次更新之间生成固定样本数 trigger_parameter_sync_step × require_batches × ppo_mini_batch_size - > 0 → 异步。上限为 (1+staleness_threshold) × (上式) - num_staleness_sample

    官方建议把这个值设成小于 1，否则精度会掉。

    5.5 实测加速比¶

    Qwen2.5-Math-7B，max_response_length ≈ 28K：

    资源 切分 400 步加速比
    32 GPU 16:16 2.66×
    64 GPU 32:32 1.92×
    128 GPU 64:64 2.35×

    128 GPU 上的模式对比：

    模式 耗时 加速
    Colocate 同步（基线） 1d 16h 48m 1.0×
    Stream off-policy 1d 1h 53m 1.6×
    Async stream + stale + partial 17h 22m 2.35×

    Qwen3-30B-A3B-Base（8K response，96:32 资源切分）：1.72×

    核心规律：序列越长，加速越明显（长尾效应越显著）。这也说明：如果我们的任务 response 短（<4K），异步的收益有限，不值得引入复杂度。

    5.6 权重同步¶

    0.7 里 one-step-off-policy 和 fully-async 都改为通过 checkpoint engine 同步权重，带 bucketing 和 pipelining。Checkpoint Engine 两个后端：NCCL（broadcast）、NIXL（P2P）。

    设计动机与 Laminar、AReaL、StreamRL、LlamaRL、PipelineRL 一致：解耦 rollout 与训练换来弹性 rollout 伸缩、容错、异构硬件支持。

    6. Agent Loop 与多轮 / 工具调用¶

    6.1 定位与破坏性变更¶

    Agent Loop 在 0.4.2 引入（alpha），是"多轮 rollout 和 agentic RL 的通用接口"。注意 0.7 的破坏性变更：SPMD rollout 模式被移除，server mode 成为默认且唯一。 官方理由是 agentic、多轮场景让旧路径"力不从心"。

    Server mode 的行为像在线服务而非离线批推理，逐样本客户端请求 → 动态 batching + 更好的多轮吞吐。附带好处是不需要侵入式修改推理引擎，接 vLLM / SGLang / TensorRT-LLM 都更容易。

    设计边界很清楚——明确不管"工具怎么定义、怎么调用"，那是用户的事。

    6.2 自定义 Agent Loop¶

    只需实现一个方法：

    class AgentLoopBase(ABC):
    @abstractmethod
    async def run(self, sampling_params: dict[str, Any], **kwargs) -> AgentLoopOutput:
        ...

    **kwargs 携带 verl.utils.dataset.RLHFDataset 的数据集字段。run 内部可以自由调 LLM、打工具（web search / DB / 代码沙箱）、与环境交互、做反思。

    返回 AgentLoopOutput 三个字段： - prompt_ids - response_ids（LLM token + 工具返回 token） - response_mask（生成 token 为 1，工具返回 token 为 0）

    内置两个：SingleTurnAgentLoop、ToolAgentLoop（ReAct 风格）。用户可自己扩展 SWEAgentLoop / GUIAgentLoop（官方 recipe 排在 v0.9）。

    一个当前限制： 一个 AgentLoopOutput 只对应一条轨迹，多轨迹输出仍在讨论中。

    6.3 执行流程¶

    PPOTrainer 采样 batch
  → AgentLoopManager.generate_sequences
    → 对所有 async LLM server 调 wake_up（同步推理引擎与训练引擎权重）
    → batch 切块分发给各 AgentLoopWorker
      → 每个 worker 为每个 prompt 起一个 AgentLoopBase 实例，驱动 run 协程
    → 汇总结果回 trainer
    → 对 server 调 sleep（释放 KV cache，权重 offload 到 CPU）

    worker 内部跑大量协程；若 worker 数等于 batch size，则每个 worker 处理一个 prompt。生成时客户端首轮选在飞请求最少的 server，之后 AsyncLLMServer 通过 IPC/RPC 与 model runner 通信。

    引擎差异： - vLLM —— Async LLM Engine 与 server 同进程，ModelRunner 与 FSDP/Megatron worker 在一起，走 ZeroMQ，server 直接调引擎 - SGLang —— Async LLM Engine 位于 FSDP/Megatron worker-0 内，派生 ModelRunner 子进程，同样走 ZeroMQ，server 远程调 worker-0

    LLMServerClient 作为多 server 代理，负责负载均衡 + sticky session（把 request_id 绑定到同一 server，保证后续轮次落在同一实例）。

    6.4 ⚠️ 必须避开的坑：token-in/token-out¶

    这是 verl 文档里最重要的一条经验，直接决定训练能否收敛。

    主流 agent 框架（LangGraph、CrewAI、LlamaIndex）都用 chat completion，把历史存成 messages。但 verl 在 DAPO（单轮）和 retool（多轮）上的实测发现：对最终 messages 重新 apply chat template 得到的 token id，与逐轮拼接的 prompt/response id 不一致。

    两个漂移来源： 1. tool parser 改写 content —— assistant content 里的 <tool_call> 块被抽成结构化 tool_calls 字段，重新编码后与原始生成的 id 不匹配 2. decode-then-encode 往返本身引入不匹配

    后果：轨迹偏离策略模型分布。文档明确报告：对最终历史 apply chat template 导致 PPO 即使在单轮场景也不收敛。

    正确做法：token-in/token-out，或 delta-based tokenization。

    6.5 多轮配置¶

    基础开关： 

    actor_rollout_ref:
    rollout:
        multi_turn: True
        name: "sglang"

    方式一：自定义工具类（有状态，需生命周期管理） —— 实现 verl.tools.base_tool.BaseTool： 

    actor_rollout_ref.rollout.tool_kwargs.tools_config_file: <tool.yaml 路径>
    工具若产出图像/视频，返回 ToolResponse 带 image/video 列表，先用 verl.utils.dataset.vision_utils.process_image / process_video 处理。

    方式二：函数工具（无状态，推荐，简单得多） 

    actor_rollout_ref:
    rollout:
        mode: async
        multi_turn:
            enable: True
            format: hermes
            function_tool_path: path/to/your_tools.py
        agent:
            default_agent_loop: tool_agent


    from verl.tools.function_tool import function_tool

@function_tool
def get_weather(city: str) -> dict:
    """Get the current weather for a city.

    Args:
        city: The city to look up, e.g. "Tokyo" or "San Francisco".
    """
    return {"temperature_c": 17.3, "condition": "drizzle"}

@function_tool("calculator")          # 显式覆盖名字
def calculator(expression: str) -> str:
    """Evaluate a Python-style arithmetic expression.

    Args:
        expression: A Python-style arithmetic expression, e.g. "(3+4)*5".
    """
    return str(eval(expression, {"__builtins__": {}}, {}))

    schema 靠 transformers.utils.get_json_schema() 从类型标注 + Google 风格 docstring 推断，支持基础类型、泛型（list[T]、dict[K,V]）、union、Optional、Literal。返回值可以是 str、dict、ToolResponse，或元组 (response, reward) / (response, reward, metrics)——元组形式可以让工具直接贡献奖励，这个设计很实用。

    function_tool_path 与 tool_config_path 可共存，启动时合并成一个 registry。

    6.6 tokenization 一致性检查¶

    verl 用 delta-based tokenization 识别 assistant token：

    prev = tokenizer.apply_chat_template(messages[:i], add_generation_prompt=True,  tokenize=False)
curr = tokenizer.apply_chat_template(messages[:i+1], add_generation_prompt=False, tokenize=False)
token_ids += tokenizer.encode(curr[len(prev):], add_special_tokens=False)
loss_mask += [1] * len(token_ids)

    自带 sanity check： 

    actor_rollout_ref.rollout.multi_turn.tokenization_sanity_check_mode: "ignore_strippable"
# 可选："strict" | "ignore_strippable" | "disable"

    特殊情况——reasoning content 剥离： Qwen/QwQ-32B、Qwen3 这类模型的 chat template 对 <think> 标签的剥离行为不一致，verl 对它们回退到固定的基础对话：

    BASE_CHAT_HISTORY = [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user",   "content": "I am a user."}
]

    默认训练用含 reasoning 的完整回答。若要与生产推理（无 reasoning）对齐： 

    actor_rollout_ref.rollout.multi_turn.use_inference_chat_template: True

    多模态数据集处理： 多轮 RL 里工具会动态产出模态，此时建议关掉预处理： 

    return_multi_modal_inputs: False    # 默认 True（数据集预处理好 image/video tensor）

    7. MTP（Multi-Token Prediction）支持 ⭐¶

    这是用户特别关注的部分，也是本报告需要说得最直白的部分：verl 的 MTP 目前处于"能跑、但约束多、且收益尚不明确"的阶段。

    7.1 支持范围与硬约束¶

    支持的模型： mimo-7B-RL、Qwen-next、DeepSeek 系列

    两个硬约束：

    1. 训练引擎：只支持 mbridge/Megatron-Bridge + megatron 组合——文档原话是"Only supports"，其他组合都不兼容。FSDP 路线用不了 MTP。
    2. 推理引擎：任意引擎均可，前提是模型在该引擎自己的兼容列表里。

    7.2 依赖版本（最大的实操障碍）¶

    组件 要求
    mbridge PR #62 的补丁（已合入 main）
    Megatron-Bridge PR #2387，mimo-7B-RL 需要（尚未合并）
    Megatron-LM dev commit 23e092f41ec8bc659020e401ddac9576c1cfed7e（加入 MTP + CP 训练）
    SGLang 分支 fix_mtp_update_weights_from_tensor（PR #17870，修 MTP 权重按 tensor 更新时的 OOM）

    这意味着要跑 MTP 得手动拼一套非发布版环境，其中还有未合并的 PR。工程上不便宜，需要预留调试时间。

    7.3 四种使用场景与配置¶

    所有配置键都在 actor_rollout_ref.model.mtp 前缀下。

    场景一：只加载 MTP 权重（不训练） 

    actor_rollout_ref.model.mtp.enable: True
    代价是额外显存；好处是导出的 checkpoint 带 MTP 模块，可直接在线部署（部署时享受 MTP 加速）。

    场景二：全参数 MTP 训练

actor_rollout_ref.model.mtp.mtp_loss_scaling_factor: 0.1

    场景三：仅训练 MTP（冻结 encoder，loss 只作用于 MTP 参数） 

    actor_rollout_ref.model.mtp.enable: True
actor_rollout_ref.model.mtp.enable_train: True
actor_rollout_ref.model.mtp.detach_encoder: True

    场景四：MTP 加速 rollout

    vLLM：

actor_rollout_ref.model.mtp.enable_rollout: True
actor_rollout_ref.model.mtp.method: "mtp"

    SGLang：

actor_rollout_ref.model.mtp.speculative_num_steps: 2

    7.4 官方实测结论（重要，且有点反直觉）¶

    训练效果方面（mimo-7B-math，max_response_length=8k）：

    只有一种配置真正改变了训练结果：base model 自带 MTP 参数 + loss 作用于全部参数 + scaling factor = 0.1。

    以下配置没有可测量的差异： - base model 不带 MTP 参数 - 带 MTP 参数但不训练 - 训练 MTP 但 scaling factor = 0 - 训练 MTP 且 detach encoder，factor = 0.1

    但文档的推荐却是 detach_encoder=True。 这里存在一个张力：唯一有效果的配置是全参数训练，而推荐的配置在他们自己的实验里没有效果差异。我的理解是推荐 detach 是出于稳定性和不干扰主任务的考虑（detach 后 MTP 训练不会污染主 loss 的梯度），而非追求指标提升。如果我们要用，建议两种都跑 ablation，不要盲信推荐值。

    rollout 加速方面（这条最需要注意）：

    开 MTP 后接受率提升约 14%，但吞吐没有跟上。在 H20 上跑 mimo-7B + SGLang，rollout 吞吐掉了约一半。

    原因归结到 tensor core 算力：H20 只有 148 FP16 TFLOPS，而 H800 是 1671、H200 是 1979。 投机解码是"用算力换延迟"，H20 这类算力受限的卡上这笔交易不划算。

    官方当前建议：推理阶段先别开 MTP 加速。 rollout 阶段的投机逻辑还在优化中。

    7.5 SFT 场景¶

    SFT 支持 MTP，配置键与 RL 完全相同。示例脚本： 

    examples/sft/gsm8k/run_mimo_7b_mtp_megatron.sh

    结果：mimo-7B-math + gsm8k 上，MTP 层对主 loss "影响有限"，但 detach 后 mtp_loss 收敛到更高的点。

    贡献方是 meituan-search，图表和 wandb 记录在 verl-community 仓库和 hou-zg-meituan 的 wandb 项目下。

    7.6 MTP 在 RL 中的核心难题（学术侧背景）¶

    verl 文档没讲透为什么 MTP 在 RL 里这么难。补充这个背景，对我们判断值不值得投入很关键：

    核心问题：RL 训练过程中 MTP 的接受长度会快速退化。

    一篇 ACL 2026 Findings 直接点明了两个卡点："vanilla 预训练模型中缺少 MTP" 以及 "RL 训练中 MTP 接受长度的快速退化"（ACL 2026）。Accelerating RL Training via MTP with Rejection Sampling 报告了同样的观察，并指出这限制了 rollout 加速的上限。

    机制上的矛盾很清楚： RL rollout 是生成瓶颈，MTP 看起来是"免费加速"；但 RL 过程中策略持续漂移，而策略漂移恰恰会破坏 draft head 与 target 的对齐。这是一个内生冲突，不是实现 bug。

    已有的应对： 美团 + 中科院的工作在 RLVR 过程中联合训练 MTP heads 并校准 loss 系数，代码在 MarkXCloud/RL-MTP（论文）。这个工作把 MTP 训练拆解成三种范式——Detach、Cross-Entropy loss、Policy loss——并解释了各自成功/失败的原因。其中的判断是：policy loss 与 RL 目标对齐得更好，但存在实际困难。这个三分法正好对应 verl 里 detach_encoder 和 mtp_loss_scaling_factor 两个旋钮背后的设计空间。

    另一个值得知道的反驳： 有工作挑战"draft 是免费的"这一普遍假设，指出在百万 token 上下文下 draft 的 KV cache 开销会变成真实的税（arXiv:2607.21535）。

    正面参考： FastMTP 报告在 7 个 benchmark 上平均 2.03× 加速且输出无损，比 vanilla MTP 改善 82%（arXiv:2509.18362）。Google 在 Gemma 4 上把 31B target 配 MTP head 作轻量 drafter，用来吃掉空闲算力（blog）。EntMTP 还提到 MTP 的一个附带好处：提升训练数据密度并改善生成质量，这个收益与解码加速无关（arXiv:2606.27550）。

    7.7 我对 MTP 的落地判断¶

    分三种情况：

    我们的目标 建议
    想让最终模型带 MTP 能力便于部署加速 ✅ 值得做。用场景一（只加载不训练）或场景二（全参训练，factor=0.1）。导出的 checkpoint 直接带 MTP 模块
    想用 MTP 加速 RL 训练本身的 rollout ⚠️ 暂缓。官方明确不推荐，H20 上还会掉一半吞吐。等 v0.8 的「MTP RL 训练」和 rollout 投机逻辑优化
    想借 MTP 提升模型质量 ⚠️ 证据不足。verl 的实验里只有一种配置有可测量差异，SFT 里对主 loss "影响有限"

    前置条件检查： 1. 我们是不是走 Megatron 路线？（不是的话 MTP 直接不可用） 2. 我们的卡是什么？（H20 这类低 tensor core 算力的卡，rollout 加速是负收益） 3. 能不能接受手动拼未发布依赖？（含未合并 PR）

    最实用的一条：关注 v0.8。 官方路线图明确列了「MTP RL 训练」，等它进主线会省掉大量环境搭建成本。

    8. 低精度：FP8 与 NVFP4¶

    8.1 两种 FP8 模式¶

    模式 训练 Rollout
    FP8 Rollout Only BF16 FP8
    FP8 End-to-End FP8（Megatron） FP8（vLLM）

    量化方案： blockwise，即 DeepSeek 方案——激活 1×128 量化，权重 128×128 量化。

    rollout-only 模式下 verl 给 vLLM 打了补丁，在生成时即时量化权重，替换 Fp8LinearMethod.process_weights_after_loading；SGLang 不需要这个补丁（原生加载量化权重）。

    E2E 模式通过 Transformer Engine 把 FP8 扩展到前反向 + FP8 优化器状态 + FP8 vLLM 推理。注意：报告的实验里 MoE router 在 vLLM 和 Megatron-Core 两侧都保持 BF16。

    8.2 配置¶

    Rollout-only（推荐起点）： 

    rollout.quantization: "fp8"
    CLI：actor_rollout_ref.rollout.quantization=fp8

    SGLang 跳过某些层：环境变量 SGLANG_FP8_IGNORED_LAYERS（逗号分隔），或模型的 quantization_config.ignored_layers（接受层名、完整路径、re: 正则）。被跳过的模块保持 rollout dtype。启动时和权重同步时规则一致。

    End-to-End： 

    actor_rollout_ref.actor.megatron.override_transformer_config:
  fp8: "hybrid"            # 或 "e4m3"
  fp8_recipe: "blockwise"
actor_rollout_ref.actor.optim.override_optimizer_config:
  fp8_recipe: "blockwise"
actor_rollout_ref.rollout:
  quantization: fp8
    要求：CUDA 12.9+、带 blockwise FP8 的 Transformer Engine 构建、NVTE_FP8_BLOCK_SCALING_FP32_SCALES=1。

    8.3 支持范围¶

    • Rollout-only： dense + MoE、async rollout 接口、vLLM 0.10.x/0.11/0.12、SGLang 0.5.5、FSDP 和 Megatron 都行
    • E2E： 仅 Megatron（经 Megatron-Bridge），已在 Qwen3-30B-A3B 和 Qwen3-8B 上验证

    8.4 实测结果（含最关键的一条警告）¶

    Qwen3-8B-Base（DAPO、AIME24、8×H100、token-level TIS，C=2）： - 开 TIS 时 FP8 rollout 精度与 BF16 齐平 - 不开 TIS 时有"明显的精度下降" ← 这条最重要 - rollout 吞吐：CUDA 12.6 + DeepGemm 提升约 12%；CUDA 12.9 最高约 18%

    Qwen3-30B-A3B-Base（2×8×H100、async FP8 rollout、vLLM + FSDP）： - rollout 加速 超过 35% - token-level TIS 下精度与 BF16 相当 - MoE 的 mismatch 普遍更高，即使 BF16 也需要校正

    Qwen3-30B-A3B E2E（2×8×H100、CUDA 12.9、prompt batch 128、n=16、20K max response）： - 精度紧跟 BF16 基线 - mismatch KL 排序：FP8 rollout-only > FP8 E2E > BF16 E2E——官方归因于 E2E 让训练和推理的精度保持了一致

    8.5 结论¶

    FP8 rollout 是当前性价比最高的降本手段（12%–35% rollout 加速），但必须与 rollout correction 配套使用。 单独开 FP8 不开 TIS 会掉精度。这是 §4 和 §8 之间的强耦合关系。

    另有 NVFP4 QAT 支持（low_precision/nvfp4_qat）。完整 ablation 见 FP8-RL 技术报告（Qiu et al., arXiv:2601.18150），脚本在 verl-recipe 的 low_precision 目录。

    9. 大模型性能调优要点¶

    摘自官方 DAPO + Qwen3-235B 最佳实践（更新于 2025-11-03），挑出容易踩坑的部分。

    9.1 显存预算的算法¶

    • bf16/fp16 下每参数约 2/TP 字节
    • 若保留 FP32 master weights 或不开优化器 offload，Adam 再加 4–8 字节/参数
    • 激活量 ∝ micro_batch_size × sequence_length × hidden_size

    并行策略优先级： TP 优先 → 需要时加 PP → CP 处理长序列 → MoE 的 EP/ETP 与 TP 对齐 → 紧张集群上 DP 最小化。

    KV cache 的约束条件： 

    memory_per_gpu × gpu_memory_utilization × TP > 2 × model_parameters
    逐步提高 TP 换 KV cache，但 TP > 8 之后要留意通信开销。

    9.2 采样参数¶

    训练 rollout： temperature=1.0、top_p=1.0、top_k=-1

    验证： temperature=1.0、top_p=0.7、top_k=-1、do_sample=True、n=1；AIME24 这类小集合把 n 推到 64。

    ⚠️ 验证时温度不要设 0 —— 会导致重复的推理循环。这个坑很常见。

    9.3 vLLM 侧¶

    enable_chunked_prefill: true
max_num_batched_tokens: max(8192, max_prompt_length + max_response_length, max_model_len)
enforce_eager: true                       # 显存紧张时；CUDA graph 显存不计入 gpu_memory_utilization
cudagraph_capture_sizes: [1,2,4,8,16,32]  # 默认 null，压力大时试这个
gpu_memory_utilization: 0.8~0.9           # 开 offload 的情况下

    注意： 有些后端参数（如 pipeline_parallel_size）可能不支持；TP=32 时 enable_expert_parallel=True 反而会拖慢 DeepSeek-V3 的 rollout。额外后端参数用 + 前缀传：+actor_rollout_ref.rollout.engine_kwargs.vllm.*。

    9.4 Megatron 侧推荐配置¶

    优化器（大模型如 DeepSeek 上收益明显）：

    9.5 checkpoint 格式的选择（容易搞错）¶

    actor_rollout_ref.actor.megatron.use_mbridge: true    # 默认
    - true —— 经 Megatron Bridge 以 HF 格式存取权重，save_contents 里 hf_model 与 model 去重 - false —— 走 Megatron dist_checkpointing，拒绝 hf_model，事后用 verl.model_merger 合并 - 无论哪种，优化器、LR scheduler、RNG state 始终走 dist_checkpointing - legacy 的 use_dist_checkpointing=True 等价于 use_mbridge=False

    另外 vanilla_mbridge 保持 false（用 Megatron-Bridge），true 走已废弃的 mbridge。

    9.6 动态 batching（建议全开）¶

    actor_rollout_ref.actor.use_dynamic_bsz: true
actor_rollout_ref.rollout.log_prob_use_dynamic_bsz: true
actor_rollout_ref.ref.log_prob_use_dynamic_bsz: true
actor_rollout_ref.rollout.log_prob_max_token_len_per_gpu: <≥ max_prompt+max_response 的倍数>

    ref 模型的五个 Megatron 并行度必须与 actor 保持一致，ref.megatron.param_offload 也建议镜像 actor 的设置，便于容量规划。

    9.7 数据要求¶

    • 只接受 Parquet。 用 examples/data_preprocess 转换
    • data_source 字段必须有对应的 reward function
    • BytedTsinghua-SIA/DAPO-Math-17k 开箱可用
    • data.truncation：多数场景用 left，严格校验用 error

    奖励系统（0.7 重构）¶

    • 支持混合奖励场景：生成式、判别式、rule-based 及其组合
    • 奖励模型重构为 server mode，可共置或独立部署
    • 新增 reward manager：limited 模式（控制请求速率）、remote 模式（CPU 密集打分外置）

    这个重构对我们的意义：如果奖励计算是 CPU 瓶颈（比如跑测试用例、调用外部 verifier），remote 模式可以把它从 GPU 节点上摘出去。

    12. 落地建议：分阶段路线¶

    阶段一：建立可信基线（1–2 周）¶

    1. 走 on-policy 流水线 + FSDP 后端（Day-0 模型支持，环境最简单）
    2. 跑通 GSM8K quickstart，确认端到端链路
    3. 打开 calculate_log_probs: true，只观测不校正，摸清我们的训练-推理 gap
    4. 建 dashboard：rollout_corr/kl、rollout_is_mean、eff_sample_size、entropy、pass@1 与 pass@k
    5. 开 full determinism，后续才能区分"改动有效"和"随机波动"

    阶段二：算法侧低成本收益（1 周）¶

    1. clip_ratio_low=0.2 / clip_ratio_high=0.28（Clip-Higher）
    2. loss_agg_mode: token-mean 确认
    3. Dynamic Sampling（filter_groups.enable=true + 3× 超采样）
    4. 按第一步测出的 gap 决定是否上 rollout correction 预设（推荐从 bypass_ppo_clip() 起）

    阶段三：按需求分叉¶

    如果瓶颈是训练速度： - response 长（>8K）→ 上 one-step-off-policy（+20–40%），再考虑 fully-async（最高 2.66×） - 想降成本 → FP8 rollout（+12–35%），必须同时开 TIS

    如果瓶颈是模型能力： - 熵坍塌 → KL-Cov - MoE 不稳 → 切 GSPO + router replay（这两个是 MoE RL 的组合拳） - 关键 token 学不到 → CISPO 或 SAPO - pass@k 退化 → 加多样性目标，延长训练（ProRL 结论）

    如果要做 agent / 多轮： - 用 @function_tool 起步（比 BaseTool 简单得多） - 务必 token-in/token-out，别用 message 历史重新 apply chat template - 打开 tokenization_sanity_check_mode

    如果要 MTP： - 先确认走 Megatron 路线（否则不可用） - 目标是"产出带 MTP 的部署 checkpoint" → 场景一/二可做 - 目标是"加速 RL rollout" → 暂缓，等 v0.8

    阶段四：跟进 v0.8¶

    • TensorDict 替代 DataProto（去 padding）
    • MTP RL 训练进主线
    • TransferQueue 成为默认
    • DeepSeek V3.2 支持

    代码风格建议：现在就按新 model engine 写，避免 v0.8 废弃 fsdp_workers.py / megatron_workers.py 时返工。
